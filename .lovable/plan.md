
## Мета
Зібрати та підтримувати актуальну базу історичних свічок по 7 основних Forex-парах, достатню для:
- бек-тесту стратегій (5-15 років D1/H4),
- денного/сесійного аналізу (2 роки H1, 6-12 міс M15),
- навчання агентів (RAG + surprise_ratio на реальній історії).

## Що маємо зараз
- `forex_ohlcv` — свічки, але заповнюються лише кнопкою «Завантажити історію», максимум ~200-400 барів на TF.
- `forex_prices` — тік поточної ціни, оновлюється кожні 5 хв (не OHLC).
- Джерело: Twelve Data (free-tier: 8 req/min, 800 req/day, history ~5000 барів за запит).

Тобто **немає ні глибокої історії, ні постійного накопичення нових свічок**.

## План — 3 етапи

### Етап 1. Одноразовий бекфіл історії (chunked)
Нова edge-функція **`backfill-ohlcv`** що:
1. Приймає `{ pair, timeframe, from, to }`.
2. Тягне з Twelve Data порціями по 5000 барів (`start_date`/`end_date`), паузи 8-10 с між запитами (ліміт 8 req/min).
3. Upsert у `forex_ohlcv` по `(symbol, timeframe, bar_timestamp)` — щоб не було дублів.
4. Продовжує в фоні через `EdgeRuntime.waitUntil` + логує прогрес у нову табличку `backfill_jobs` (status, done_bars, total_est, last_ts, error).

**Обсяг за замовчуванням:**
| TF  | Глибина | ~Барів на пару | 7 пар |
|-----|---------|----------------|-------|
| D1  | 15 років | ~3 900 | ~27 000 |
| H4  | 5 років  | ~7 800 | ~55 000 |
| H1  | 2 роки   | ~12 500 | ~87 000 |
| M15 | 6 місяців | ~12 000 | ~84 000 |

Разом ~250k рядків — це дрібниця для Postgres.

### Етап 2. Постійне накопичення нових свічок (cron)
Нова edge-функція **`ingest-ohlcv-recent`** — щохвилини/щогодини тягне тільки **останні N закритих барів** і робить upsert:
- M15 → cron `*/15 * * * *` (тягне 2 останні M15)
- H1 → cron `5 * * * *` (2 останні H1)
- H4 → cron `5 */4 * * *`
- D1 → cron `10 0 * * *` (після закриття NY)

Так база сама себе доповнює 24/5, без ручних кнопок. Weekend-guard: не смикати API у сб/нд.

### Етап 3. UI + індекси
- Індекс `(symbol, timeframe, bar_timestamp DESC)` + `UNIQUE (symbol, timeframe, bar_timestamp)` — гарантія цілісності.
- На сторінці Профіль/Адмін — картка «Data coverage»: для кожної пари+TF показати `MIN/MAX(bar_timestamp)`, `COUNT(*)`, і кнопку «Запустити бекфіл» (за діапазоном).
- Кнопка «Завантажити історію» на головній залишається, але тепер тягне через `backfill-ohlcv` (все правильно й без дублів).

## Технічні деталі
- **Rate-limit**: черга з паузою `sleep(8500ms)` між викликами Twelve Data. При 429 → експоненційний бекоф.
- **Idempotency**: `INSERT ... ON CONFLICT (symbol,timeframe,bar_timestamp) DO UPDATE`.
- **Обмеження free-tier Twelve Data**: 800 req/day. Повний бекфіл (~200 запитів) укладається в один день; можна розбити на кілька днів через `backfill_jobs.status='paused'`.
- Якщо в майбутньому впремося в ліміт — легко підключити другого провайдера (Polygon/Alpha Vantage) як фолбек у тій же функції.

## Що НЕ входить (окремим кроком, якщо треба)
- Тик-дані (Dukascopy дампи) — надлишок для нашої стратегії.
- Партиціювання по роках — знадобиться коли перевалимо 5-10M рядків, зараз ні.
- Історія економічного календаря / новин.

## Порядок робіт
1. Міграція: `UNIQUE`-індекс на `forex_ohlcv`, таблиця `backfill_jobs`.
2. Edge `backfill-ohlcv` + `ingest-ohlcv-recent`.
3. Cron-розклад для `ingest-ohlcv-recent` (4 задачі).
4. UI-картка «Data coverage» у Профілі.
5. Запуск першого бекфілу D1×15y для всіх 7 пар (перевірка), далі решта TF.
